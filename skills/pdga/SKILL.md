# PDGA Tournament Operations Skill

Query the PDGA Services API for events, players, courses, and growth statistics. Export registration data from any DiscGolfScene tournament. Manage DGS tournaments programmatically (auth, descriptions, images). Generate tee time sheets with pool assignments, card requests, and division ordering. Publish to Google Sheets with pool colors.

## How it works

**PDGA API** requires authentication (a PDGA account with Services API access), read from:
1. Environment variables: `PDGA_USERNAME` and `PDGA_PASSWORD`
2. Or a JSON file named by `PDGA_CONFIG` — either `{"username": "...", "password": "..."}`
   or `{"PDGA": {"Services": {"Username": "...", "Password": "..."}}}`

`PDGA_STATE` (optional, e.g. `CA`) sets the default `--state` for the search/count commands.
There is no built-in default state.

Rate limit: 300ms between requests. Max 200 results per page (pagination handled automatically).

**DiscGolfScene** uses session cookies:
1. `~/.dgs-cookies.json` (or the path in `DGS_COOKIE_FILE`) — generated by `dgs-auth.py`; used by
   the `dgs-*.py` management scripts (preferred)
2. Env vars: `DGS_COOKIE_AUTH`, `DGS_COOKIE_CR`, `DGS_COOKIE_CM` — used by `pdga.py
   dgs-registrations`, and as the fallback for `dgs-tournament.py`

Additional env vars:
- `DGS_EVENT_SLUG` — default event slug (optional, can pass `--event-slug` per command)
- `DGS_EMAIL` — login email for `dgs-auth.py`
- `DGS_PASSWORD` — login password for `dgs-auth.py`

Cookies expire periodically. When they do, re-run `dgs-auth.py` to refresh them.

## Commands

All commands are run via `python3 <skill-dir>/scripts/pdga.py <command> [args]`.

### Events

Search PDGA events (tournaments, leagues, etc.).

```bash
# Upcoming events in a state (excludes leagues by default when using event-count)
python3 scripts/pdga.py events --state CA --start-date 2026-05-01

# Events in a specific date range
python3 scripts/pdga.py events --state CA --start-date 2025-01-01 --end-date 2025-12-31

# Exclude league-tier events
python3 scripts/pdga.py events --state CA --exclude-tiers L,XL

# Only A-tier and above
python3 scripts/pdga.py events --state CA --tier A
```

Returns: tournament_id, tournament_name, city, state_prov, start_date, end_date, tier, status, format, tournament_director, class, total_players.

### Event Detail

Get details for a specific event by tournament ID.

```bash
python3 scripts/pdga.py event-detail 12345
```

### Event Count (Growth Tracking)

Count events by year for a state — useful for growth charts and infographics. **Excludes L and XL (league) tiers by default** since weekly leagues skew the count.

```bash
# A state's events 2020-2026, excluding leagues
python3 scripts/pdga.py event-count --state CA --start-year 2020 --end-year 2026

# Include all tiers (leagues too)
python3 scripts/pdga.py event-count --state CA --exclude-tiers ""

# Only count specific tiers
python3 scripts/pdga.py event-count --state CA --exclude-tiers "L,XL,C"
```

Returns: `{"2020": 30, "2021": 55, ...}` — JSON object keyed by year.

### Players

Search PDGA players.

```bash
# Look up a specific player
python3 scripts/pdga.py player-detail 12345

# Search by name
python3 scripts/pdga.py players --first-name Jane --last-name Doe

# Players in a state (note: state_prov filter can be unreliable per PDGA API docs)
python3 scripts/pdga.py players --state CA --limit 500
```

Returns: pdga_number, first_name, last_name, city, state_prov, country, rating, class, member_status, official_status.

### Player Count

Count total PDGA players for a state. Paginates through all results.

```bash
# Total PDGA registrations in a state
python3 scripts/pdga.py player-count --state CA

# Only current members
python3 scripts/pdga.py player-count --state CA --status current
```

Returns: `{"state": "CA", "count": 5200}`

**Note:** The `state_prov` filter on the PDGA API is known to be unreliable — it may return players from other states. Results are a ballpark, not exact. For precise state counts, use the PDGA website player search with curl and a browser User-Agent.


### DGS Registrations

Export and parse registration data from any DiscGolfScene tournament you admin.

```bash
# Download + parse registrations for the default event (DGS_EVENT_SLUG)
python3 scripts/pdga.py dgs-registrations

# Specify a different event
python3 scripts/pdga.py dgs-registrations --event-slug "My_Tournament_2026"

# Save the raw CSV to a file while also getting parsed JSON
python3 scripts/pdga.py dgs-registrations -o .raw/registrations-2026-05-23.csv

# Output raw CSV instead of parsed JSON
python3 scripts/pdga.py dgs-registrations --raw

# Parse a local CSV file (no download)
python3 scripts/pdga.py dgs-registrations --file ~/Downloads/some-export.csv
```

Returns JSON with: confirmed/waitlisted counts, pro/am breakdown, per-division detail, entry fees, auto-detected add-on totals (chairlift, VIP, food vouchers, etc.), and waitlisted player names.

**Waitlist gotcha:** DGS uses `'1'` in the Waitlist column for waitlisted players, not `'YES'`. The parser handles both.

**Add-on auto-detection:** Any CSV column ending in ` $` (other than `Entry fee $`) is treated as an add-on. This works across events with different add-on configurations — no hardcoded column names.


Returns: event title, URL, and registered player count (if visible on the page).

### Layout

Pull normalized course layout data (holes, pars, distances, notes) from **PDGA Live**
(any event with live scoring — numeric TournID) or **Parkdly** (caddie-book or
destination URL — delegates to the `parkdly` sibling skill). Both sources emit the
same schema, consumed by `build-scorecards.py`.

```bash
# PDGA Live: all unique layouts for an event, deduped across divisions × rounds
python3 scripts/pdga.py layout 12345

# PDGA Live: one division/round
python3 scripts/pdga.py layout 12345 --division MPO --round 1

# Parkdly destination: every course's named layouts (FPO, B Pool, ...), one JSON per layout
python3 scripts/pdga.py layout "https://parkdly.com/p/<destination>" --out-dir ./layouts

# Parkdly: filter by course and/or layout name; --base adds the base course layout
python3 scripts/pdga.py layout "https://parkdly.com/p/<destination>" --course <course-name> --layout FPO
```

Normalized schema per layout:

```json
{
  "source": "pdga-live | parkdly",
  "event": "...", "course": "...", "layout": "A Pool - Day 1",
  "notes": "layout-level notes (PDGA Live) or null",
  "used_by": [{"division": "MPO", "round": 1}],
  "holes": [{"seq": 1, "label": "10A", "par": 3, "distance_ft": 235, "notes": "tee-sign text or null"}],
  "totals": {"holes": 21, "par": 63, "distance_ft": 5340}
}
```

**Source differences:** PDGA Live carries real play-order hole labels (e.g. `10A`),
pool-named layouts, and layout-level notes, but **no per-hole tee-sign notes** — and
only exists for events that used PDGA live scoring. Parkdly carries per-hole tee-sign
notes (OB/mando rules) and named layouts, but only for courses built in Parkdly. For
Parkdly, named layouts are emitted by default (they are the tournament layouts); the
base course layout is emitted only with `--base` or when no named layouts exist.

### Scorecards

Generate printable scorecards from layout JSON: page 1 = scorecard 3-up, page 2 =
hole notes / OB rules 3-up. Print duplex, cut into thirds.

```bash
# Every course's pool layouts in your event colors, straight to PDF
python3 scripts/pdga.py layout "https://parkdly.com/p/<destination>" --out-dir ./layouts
python3 scripts/build-scorecards.py ./layouts/layout-*.json \
  --title "2026 My Open" --colors "#1f3a5f,#2a9d8f,#e9c46a" \
  --players 4 --logo ./assets/my-event-logo.png \
  --out-dir ./scorecards --pdf
```

Flags: `--title` (card header; default = layout's event name), `--subtitle` (extra
meta, e.g. a date), `--players N` (blank rows, default 5), `--colors`
(comma-separated header hexes cycled across files — light tints, zebra stripes, and
text contrast are derived automatically, so light brand colors like yellow get dark
text), `--flip long|short`, `--logo PATH`, `--out-dir`, `--pdf` (headless Chrome; set
`CHROME_PATH` if not auto-found).

**`--flip` (notes-page orientation, default `long`):** The hole-notes page aligns
behind its scorecard by one of two equivalent duplex schemes. `long` (default) keeps
the notes page **upright** — it reads right-side-up on screen, and prints correctly
when you duplex **flip on the LONG edge**. `short` rotates the notes page 180° for the
legacy **short-edge** flip (the notes page looks upside
down in the PDF). Prefer `long` unless a printer is locked to short-edge duplex.

**`--logo PATH`** (optional, no default — omit it for a logo-free card): Embeds a logo
(SVG/PNG/JPG) in each card header as a base64 data URI (self-contained — no external
files at print time). Use a **tightly-cropped**
asset; logos with baked-in canvas padding render small. To trim padding from a padded
SVG: `rsvg-convert -w 2000 in.svg -o raw.png` then PIL `Image.getbbox()` + `crop()`.

Player rows are a fixed 40px writing height (not stretched to fill the third), leaving
buffer between the last row and the cut line. Long tee-sign note sets auto-shrink the
notes font so each card stays inside its 1/3-page slot; the redundant "Hole Notes:"
prefix from Parkdly is stripped. A layout with no notes at all produces a front page
only.

Take `--colors` from the event's own brand guide rather than guessing.

### PDGA Live scorecard images (share export)

PDGA Live's per-player **Share scorecard** image (event header, place, total, event rating and prize,
then every round hole by hole) for recaps, social posts and blog pages. **There is no URL for it:** the
page draws the PNG in the browser (no network request), so it must be driven through the UI. The script
does that headless:

```bash
python3 scripts/live-scorecard-export.py 12345 MP40 "Jane Doe" "John Roe" --out ./scorecards
python3 scripts/live-scorecard-export.py 12345 MPO "Alex Example" --layout summary
```

- One PNG per player covers **every round** (1592 px wide), named by PDGA, e.g.
  `jane-doe-my-tournament-2026-scorecards.png`. `--layout summary` gives the stat-dial version.
- Names as PDGA Live shows them, matched ignoring spaces and punctuation (the page splits first and last
  name into separate spans, so exact-text locators miss). Run divisions in parallel as separate processes.
- UI path it automates: player row `.player-full-name` → the expanded panel's ⋮ (`a.btn-icon:has(i.pi-options-vert)`;
  the header's icon button is **event** share, a trap) → "Share scorecard" → `.pdga-bottom-sheet` → layout
  `.image-type` → Download button.
- Needs system Chrome (`channel="chrome"`) and a plain browser User-Agent. The hole-by-hole numbers behind
  the image come from `live_results_fetch_round` (see Layout); use the JSON for analysis and this for pictures.

### Flyover

Render caddie-book flyover videos for a tournament's courses. This command is a thin
orchestrator over two sibling skills — it owns no Parkdly parsing or video-rendering
logic itself:

- **`parkdly`** — fetches course coordinates/geometry from a Parkdly caddie book
  (holes, tees, baskets, flight paths, OB boundaries, amenities, tee-sign notes).
- **`earth-flyover`** — renders the headless ArcGIS SceneView video (satellite
  imagery draped on real terrain), with 3D overlays and a burned-in text HUD.

```bash
# All courses in a destination (e.g. a whole tournament's caddie books)
python3 scripts/pdga.py flyover "https://parkdly.com/p/<destination>"

# Just one course, by name filter
python3 scripts/pdga.py flyover "https://parkdly.com/p/<destination>" --course <course-name>

# A single caddie-book URL directly (skips destination listing/filtering)
python3 scripts/pdga.py flyover "https://parkdly.com/p/<destination>/<course-caddie-book>"

# Vertical (Reels/Shorts/Stories), establishing orbit instead of per-hole tour
python3 scripts/pdga.py flyover "https://parkdly.com/p/<destination>" --mode establish --aspect 9:16

# One hole only, at the default 10s/hole cinematic pace -- fast way to preview a course
# before committing to a full-course render (see render-time note below)
python3 scripts/pdga.py flyover "https://parkdly.com/p/<destination>" --course <course-name> --hole 7
```

Flags: `--course` (name substring filter), `--mode establish|holes` (default
`holes`), `--overlays on|off`, `--hud on|off`, `--aspect 16:9|9:16`, `--hole N`
(render just one hole), `--seconds-per-hole` (default `10` — the main pacing knob
for the per-hole pan/settle), `--frames-per-hole`, `--frames`, `--width`/`--height`,
`--settle-ms`, `--out-dir` (default `./flyovers`). These map directly to
`earth-flyover`'s `render.mjs` flags — see that skill's `SKILL.md` for what each one
does and how the per-hole camera/HUD behave.

**Render time:** at the default 10s/hole pace, a full 18-hole course in `holes` mode
is ~5400 frames and can take **1.5-3 hours**. Use `--hole N` to iterate on
pacing/framing quickly (one hole renders in a few minutes), and treat full-course
renders as a background/overnight job.

**Output:** one MP4 per course in `--out-dir`, the fetched course JSON per course
(reusable directly with `earth-flyover` for finer control), and a `manifest.json`
listing every rendered file. Renders run sequentially (each headless Chromium
instance is CPU-heavy) — expect roughly 1-3 minutes per 18-hole course tour
depending on resolution and frames-per-hole.

**Prerequisites:** both sibling skills (`parkdly`, `earth-flyover`) must be installed next to
this skill under the same skills root (`pdga.py` looks for `../parkdly` and `../earth-flyover`).
If they are not available, the `flyover` command (and Parkdly layout pulls) will not work. Install
`earth-flyover` dependencies once from its skill directory, and ensure `ffmpeg` is on `PATH`.

## Disc Golf Scene (DGS) — Tournament Management

> This section covers DGS *tournaments*. DGS league listings use different forms and are
> out of scope here.

Separate scripts for DGS authentication and tournament management. These extend the basic DGS registration export in `pdga.py` with full admin capabilities.

### DGS Authentication

Re-authenticate with DGS and save fresh session cookies. This replaces the old browser-based cookie grabbing workflow.

```bash
# Authenticate using DGS_EMAIL and DGS_PASSWORD from .env
python3 scripts/dgs-auth.py

# Explicit credentials
python3 scripts/dgs-auth.py --email you@example.com --password yourpass

# Preview cookies without saving
python3 scripts/dgs-auth.py --dry-run

# Authenticate and update .env with new cookie values
python3 scripts/dgs-auth.py --update-env /path/to/.env

# Verbose mode (shows full login flow details)
python3 scripts/dgs-auth.py -v
```

**What it does:**
1. GETs the sign-in page to discover hidden form fields (CSRF tokens, etc.)
2. POSTs credentials to `https://www.discgolfscene.com/auth/sign-in`
3. Captures all Set-Cookie headers via `http.cookiejar`
4. Saves cookies to `~/.dgs-cookies.json`
5. Prints cookie names/values and `.env` update instructions

**Cookie file:** `~/.dgs-cookies.json` (override with `DGS_COOKIE_FILE`) — loaded automatically by `dgs-tournament.py`, `dgs-add-option.py`, `dgs-copy-tournament.py` and `dgs-tee-times-setup.py` (with priority over env vars). `pdga.py dgs-registrations` reads the `DGS_COOKIE_*` env vars.

**When to re-run:** Whenever DGS commands return HTML instead of expected data, or `check-auth` reports expired cookies.

### DGS Tournament Management

Full tournament management on DGS — 18 subcommands covering overview, divisions, registration, staff, discount codes, pools, PDGA linking, waitlist, player adds, document uploads, and cross-tournament cloning.

All commands: `python3 <skill-dir>/scripts/dgs-tournament.py <command> [args]`

Every write command supports `--dry-run` to preview what would be submitted without POSTing. All output is JSON to stdout; status messages go to stderr.

**URL patterns:**
- Public page: `/tournament/{slug}` (singular)
- Admin pages: `/tournaments/{slug}/admin/{page}` (plural + admin)
- Non-admin management: `/tournaments/{slug}/{page}` (plural, no admin)

#### Update Overview

Update any combination of tournament overview fields. Only fields you pass are included in the POST — nothing else is overwritten.

```bash
# Update name and dates
python3 scripts/dgs-tournament.py update-overview My_Tournament_2026 \
  --name "My Tournament 2026" --start-date "09/26/2026" --end-date "09/27/2026"

# Update format and tier
python3 scripts/dgs-tournament.py update-overview My_Tournament_2026 \
  --rounds 2 --format s --tier C --tier-am C --event-class ProAm --sanctioned 1

# Update description from file
python3 scripts/dgs-tournament.py update-overview My_Tournament_2026 \
  --description-file description.html

# All available flags
python3 scripts/dgs-tournament.py update-overview <slug> \
  --name --description-file --start-date --end-date --rounds --format \
  --location --sanctioned --tier --tier-am --event-class --public \
  --event-type --length --refund-instructions --welcome-message --website \
  --dry-run
```

Date format: `MM/DD/YYYY`. Format codes: `s`=Singles, `d`=Doubles, `t`=Teams, `c`=California, `a`=Ace Race, `e`=Event.

DGS has two add-on kinds on `admin/registration-form`. **Additional Items** (`tournament[addons]`) are one checkbox at one price (Ace Pot, CTP). **Options** (`tournament[options]`) are a list of choices, each with its own price and `quantity_available`, shown as a dropdown with "N available". Use an option for anything with sizes or tiers. One pick per registrant.

```bash
python3 scripts/dgs-add-option.py My_Tournament_2026 --name "Event Hoodie" \
  --description "..." --choice "Small:45:10" --choice "Medium:45:15" --choice "No thanks::" [--required] [--dry-run]
```

`--choice` is `Label:amount:quantity` (blank = free / unlimited). Posts the full form back, refuses a duplicate option name, and re-reads the form to verify every existing field came back unchanged. Cookies from `~/.dgs-cookies.json` (or `DGS_COOKIE_FILE`).

#### Clone From (convenience command)

Copy settings from one tournament to another. Reads overview, divisions, and/or registration settings from the source and POSTs them to the target. Not a DGS endpoint — a multi-step read-then-write operation.

```bash
# Clone everything (overview + divisions + registration)

# Clone only specific sections
```

Sections: `overview`, `divisions`, `registration` (default: all three).

#### Copy Tournament (create a NEW tournament)

`dgs-copy-tournament.py` creates a brand-new DGS tournament by POSTing to DGS's native `/tournaments/{slug}/copy` endpoint — the only scripted way to CREATE a tournament (everything else here manages existing ones). Prints the new tournament's slug from the redirect.

```bash
python3 scripts/dgs-copy-tournament.py \
  --source My_Tournament_2026 \
  --name "My Tournament 2026 Practice Round - Monday" \
  --date 07/13/2026            # add --public to publish immediately (default: hidden)
```

**Gotchas (all hit in real use):**
- The copy drags along the source's divisions (checked, with fees), registration options/add-ons, custom questions, **schedule events** (`events[ID][...]` on `/admin/schedule` — they render a full Schedule section + a Locations list on the public page), **all attached locations** (`tournament[location_ids][]` + paired `tournament[location_delete][]` on `/admin/overview`; delete = set the delete hidden to the location id), and **registration-phase items** (`schedule_items[ID][...]` on `/admin/registration-schedule`). Strip all of them.
- **`set-divisions` is PARTIAL-update:** posting `GEN:0` adds GEN but does NOT uncheck divisions that are already checked (the SKILL note "divisions not listed are left unchecked" only holds for a fresh event). To remove divisions, POST the full `/divisions` form browser-faithfully with the unwanted `[checked]=1` pairs dropped. The divisions form is `<form method="post" action="">` with NO class (the regform/schedule/overview forms use `class="container top-section"`); skip the `[XXX]` template-row fields.
- **A tournament must always have ≥1 attached location — the server silently refuses to delete the LAST one** (every delete variant on a sole location no-ops while the same POST's other fields save fine). To end up with a different/neutral location, ADD the replacement first (`tournament[location_ids][]=<id>` + paired `location_delete][]=0` appended to the overview POST), then delete the old id in the same or a following POST. "Zero locations" is impossible; when no real venue exists in DGS's courses-only location DB, search it (`/json/locations?view=courses/autocomplete&keywords=`) for a "To Be Announced"-style placeholder location near you.
- The PDGA link does NOT copy (safe). Create hidden, configure, verify the public page logged-out, then flip public with `update-overview --public 1`.
- **New tournaments sit in DGS's "online registration pending approval" queue (up to 48 h)** even when copied from an approved event: the registration form is staff-only until DGS staff approve it. Budget lead time; the yellow banner on the register tab is DGS's review, not a config error.

#### Tee Time Signups (self-service time slots)

`dgs-tee-times-setup.py` installs DGS's native **Tee Time registration option**: players pick their own tee time at registration, DGS enforces a per-slot player cap, and the registration page shows a public tee sheet ("8:10 am · 2/4"). Good for practice rounds (avoids the everyone-shows-up-at-once rush) and any flex-start event.

```bash
# 49 slots, 8:00am-4:00pm every 10 min, 4 players each; wipe copied options/questions first
python3 scripts/dgs-tee-times-setup.py <slug> \

```

How it works: GETs `/admin/new-tee-times-option?start=08:00am&end=04:00pm&interval=10&group_size=4` (DGS's AJAX fragment; params are `start/end/interval/group_size` — DGS's own JS hardcodes `:00` minutes on start/end), merges the generated option into a browser-faithful serialization of the FULL registration form, and POSTs it back. **Full practice-round recipe** (proven in real use): `dgs-copy-tournament.py` → `dgs-tee-times-setup.py --clean` → `update-overview` (same-day start/end, `--rounds 1 --length 1 --sanctioned 0`, location, description) → `set-divisions "GEN:0"` (GEN = General catch-all, free) → `set-registration-schedule` → `set-registration-settings --registration-allowed 1 --pdga-required 0 --validate-pdga-eligibility 0 --validate-pdga-rating 0 --registration-edits-allowed 1` → `set-waitlist --allow-waitlist 0` → verify public page → `update-overview --public 1`.

### DGS Form Gotchas

DiscGolfScene's admin forms are plain HTML posts, and two of their conventions will
silently eat a change if you assume Rails-style behaviour.

**Absent checkboxes are ignored, not treated as unchecked.** `set-divisions` sends only
the divisions you name, so it can turn divisions ON but never OFF. Removing a division
requires posting `tournament[divisions][XX][checked]=0` explicitly. The safe pattern for
any destructive change to a checkbox form is: GET the page, serialize every input as the
browser would, flip only the fields you mean to change, POST the whole thing back.

**Verified in practice:** dropping a set of age divisions needed an explicit `=0` for every
one of them. The skill command reported success and changed nothing.

**Delete fields are hidden inputs that already hold `0`.** On `admin/pictures` and
`admin/documents` each row carries `pictures[ID][delete]` / `documents[ID][delete]` as a
hidden input with `value="0"`, toggled to `1` by a trash icon. Reading the existing value
and posting it back deletes nothing. Send the literal `1`. A truthiness test on the string
`"0"` passes in most languages, which is exactly how this one gets missed.

**Caps live outside the divisions payload.** `tournament[cap_total]` is on the same page but
is not included when you post divisions alone. Pass the cap explicitly or it can blank out.

**Verify by re-reading the page, never by trusting HTTP 200.** Every one of these failures
returned 200. Parse the form back and assert the field actually holds what you sent. When
counting enabled checkboxes, match `type="checkbox"` inputs and test for a real `checked`
attribute; a naive regex over the whole tag double-counts and reports everything as on.

### Withdrawing or Re-dividing a Registrant

No `dgs-tournament.py` command yet; both are plain form posts (verified in real use). The registrant id is in `registration/edit` (`registrant[<id>][name]`).

- **Remove:** `GET /tournaments/{slug}/registration/remove-player/{id}` is a confirmation page, not an action. POST it back with `remove_player[refund]=0` ("Do not issue a refund", the default) plus the hidden refund fields as rendered and an empty `password`. `1` refunds through PayPal and needs the DGS password. Verify with a fresh export and the `/refunds` log.
- **Change division (or any field):** `registration/edit-player/{id}` holds the full registration (name, division, PDGA#, email, paid, add-ons, options, notes). Serialize the whole form as a browser would, change only `registration[registrants][1][division_code]`, POST with `continue_registration=Save Changes`, then re-read and diff: exactly one field should differ.
- **Push to PDGA TM now:** `admin/pdga-link` has a second, separate form. POST `refresh_link=Refresh Current Registration list` by itself. Don't send the settings form, whose `pdga_password` would go out blank. TM showed the change within a minute.

## Tee Time Generation

After pulling registrations via `dgs-registrations`, generate tee time assignments with pool splits, card requests, and division ordering. This skill does not ship a generator: write a small per-event `tee-times.py` (pool/division config differs every event) that reads the DGS CSV, follows the card-building rules below, and supports the CLI described under "CLI Arguments".

Useful knobs for that script: fixed early blocks at set times, `MERGE_INTO` for small divisions, `DIVISION_OVERRIDES`, `POOL_OVERRIDES`, `MANUAL_SWAPS`, `FIRST_IN_DIVISION` / `LAST_IN_DIVISION`, a self-check that every player is placed exactly once, and `--tsv` output for TM.

### Workflow

1. **Pull registrations:** `pdga.py dgs-registrations --event-slug <slug> -o ./<event>-registrations.csv`
2. **Define pools:** Map divisions to pools (A/B/C) in the tee-times script
3. **Aggregate card requests:** Check DGS registration Notes column, Gmail (`players@discgolfscene.com` emails), and DGS comments page
4. **Generate tee times:** `python3 tee-times.py --csv ./<event>-registrations.csv --start 09:00 --json`
5. **Publish to Google Sheets** (a sheet the user supplies, or a new one) with pool colors and summary tab

### Card Building Rules

These rules were developed through iteration and should be followed for all events:

| Rule | Detail |
|------|--------|
| **Division purity** | Divisions with 3+ players get their own cards — never mix to fill |
| **Spillover merging** | Divisions with 1-2 players merge with adjacent divisions in tee-time order |
| **Card sizes** | Min 3, max 5 players per card. Prefer 4s |
| **3s before 4s** | Threesomes tee off before foursomes within each division block — they play faster and won't back up |
| **Card requests** | Honor explicit requests (DGS notes, email, comments, TD sheet). Cross-division within a pool is OK. Cross-pool is DENIED |
| **Manual swaps** | Post-generation player swaps between cards in the same pool |
| **Pool overrides** | Force specific players into a different pool (e.g. `POOL_OVERRIDES = {"Jane Doe": "B"}`) |
| **Aged grouping** | Masters/Senior divisions (M/FP40+, MA40+, etc.) grouped together. Singleton aged divs (MP60, MA60) merge into the largest aged bucket |
| **Gender grouping** | Women's divisions (FPO, FA*) grouped together. Women spillover (1-2 players) stays on women's cards, not merged with men |
| **Whole divisions** | If a division fits on one card (≤5 players), keep it whole — no splitting |
| **Pool order** | Tee times go C → B → A with a configurable break between pools |
| **Waitlist filtering** | Any non-empty Waitlist column value = waitlisted (DGS uses position numbers: 1, 2, 3, not just YES) |
| **Random seeding** | Players are randomized within divisions (deterministic per-name seed), not alphabetical |
| **First/last overrides** | `FIRST_IN_DIVISION` puts a player's card first in their division block. `LAST_IN_DIVISION` puts them last (e.g. TD goes last) |

### Card Request Sources

Check all four sources and cross-reference:

1. **DGS Registration Notes** — the `Notes` column in the CSV export
2. **Email** — search the TD inbox for `from:players@discgolfscene.com subject:"<event name>" after:YYYY/MM/DD` (DGS registration notifications) for card requests in the body. Also check for requests forwarded by other staff (e.g. `subject:"card request"`)
3. **DGS Comments Page** — curl `https://www.discgolfscene.com/tournaments/<slug>/comments`
4. **TD's Google Sheet** — the TD may maintain a separate card request sheet. Check for a "Round 1 Card Requests" tab

### Google Sheets Publishing

Publish to a Google Sheet the user supplies (ask for its URL/ID — never hard-code one), or create a new one. Two tabs:

**Tee Sheet tab** (one row per card):
- Columns: Pool, Card, Tee Time, Size, Player 1–5 (as "Name (Division)"), Notes
- Pool rows colored using the event's caddie book colors
- Only color data rows — leave unused columns/rows white

**Summary tab:**
- Pool tee time ranges with player counts, card counts, first/last tee, duration
- Pool break rows between pools
- Card size distribution (3s, 4s, 5s count + player totals)
- Card requests table with status (HONORED / DENIED / MANUAL SWAP)

**Creating / filling the sheet:**
1. Use the user's sheet ID, or create a spreadsheet with whatever Google Drive tool is available
2. Write the data with a Google Sheets tool, or the Sheets API `values.update`
3. Use `gcloud auth print-access-token` + Sheets API `batchUpdate` for formatting (colors, bold, freeze, auto-resize)
4. Pool colors should match the event's own pool colors (caddie book / signage), not guesses

### PDGA Tournament Manager Upload

The `--tsv` flag generates tab-delimited data for pasting into the PDGA TM "Upload Player Data" page.

```bash
python3 tee-times.py --csv ./registrations.csv --start 09:00 --tsv | pbcopy
```

**Column headers must match PDGA TM's database column names exactly.** The available PDGA TM database columns are:

`PDGA #`, `First Name`, `Last Name`, `Division`, `Prize`, `Pool`, `Start`, `Hole`, `Tee Time`, `Declined`, `Round 1`, `Round 2`

Our TSV uses these columns (all auto-map):

| Our Header | PDGA TM Database Column | What It Is |
|------------|------------------------|------------|
| `First Name` | First Name | Player first name (may include middle) |
| `Last Name` | Last Name | Player last name (split on last space) |
| `PDGA #` | PDGA # | PDGA number (space before #) |
| `Division` | Division | Division code (MPO, MA1, etc.) |
| `Tee Time` | Tee Time | 24-hour format (09:00, 13:18) |
| `Hole` | Hole | Starting hole number |

**Important:** PDGA TM has NO single "Name" column and NO "Round" column. Names must be split into `First Name` / `Last Name`. Round is not needed for tee time uploads.

**Common mapping mistakes:**
- `Name` → no match in PDGA TM. Must use `First Name` + `Last Name`.
- `PDGA#` (no space) → won't auto-map. Use `PDGA #` (with space).
- `Tee` → maps to "Hole". Use `Tee Time`.
- `Start` → maps to "Start" (general purpose), not "Hole". Use `Hole` for starting hole.
- `Round` → no match. PDGA TM uses `Round 1` / `Round 2` for scores, not tee times.

**The upload parser requires TAB delimiters.** Comma-separated data is rejected with
"Please enter the results or the registration list in the box provided below." — the same
message you get for an empty box, so it reads like the paste failed rather than like a
format error. Typing tabs into the textarea with browser automation does not work either
(Tab moves focus), so put the TSV on the clipboard and paste it.

**Workflow:**
1. Generate TSV: `python3 tee-times.py --tsv | pbcopy`
2. Go to PDGA TM → Upload tab
3. Check "First row in results contain field names"
4. Paste from clipboard into the textarea
5. Click "Next" → verify all 6 field mappings auto-matched
6. **Player Matching page:** Players without PDGA numbers show as "New" with a match dropdown. PDGA TM matches by PDGA# first — without one, it falls back to name matching. Verify the dropdown matches are correct and submit. This is normal for non-PDGA-member players and won't create duplicates. Leave the "New" checkbox unchecked when the dropdown already names the existing registrant.
7. **Tee Time Round Selections page:** one dropdown per division (`cboRoundD<DIV>P`) choosing which round the tee times belong to. Defaults to Round 1; set Round 2 when posting Sunday's times.
8. **Summary page:** check uploaded = matched and "newly added" = 0 before the final Next. It then shows "Upload successful."
9. **Verify on PDGA Live**, not the TM page: `live-api/live_results_fetch_round?TournID=&Division=&Round=` returns `TeeTime` and `TeeStart` per player. Compare every row to the TSV.

**Browser traps (seen in practice):** clicking TM's `Next »` buttons by element ref did nothing on three of the four pages; a coordinate click from a screenshot worked every time. Fill the textarea by setting `textarea.value` from JavaScript (tabs survive), not by typing.

**Registration changes after the upload.** TM's players page says *"Until scores or tee-times are posted, registration updates should be made on DiscGolfScene.com."* In practice the DGS "Refresh Current Registration list" (below) still pushed a division change **after** tee times were posted. Either way: make the DGS change, refresh, confirm it on TM's players page, then re-upload the full TSV (it re-matches everyone, 0 new) and check PDGA Live again.

### CEP: the Competition Endowment Program

<https://www.pdga.com/td/pdga-competition-endowment-program>. C-tier only, USA and Canada,
three designations: Charity, School-affiliated, Developmental. Charity and School events
are marked **XC** because of the reduced payout. Apply at least **14 days** before the event.

Beware stale copies. The `pdga_competition_endowment_program_summmary_11_22_2021.pdf` that
still circulates says the per-player fee is $2 and applications are due 45 days out. Both
are wrong now. Use the live page and `cep_minimum_donation_calculator_v1.1.xlsx` (Jan 2026).

**Charity minimum donation per player:**

    $3 PDGA per-player fee   (donated to the charity, not kept by PDGA)
  + $3 event match
  + 25% of the remaining net entry (gross - 6), rounded UP to the dollar
  = minimum donation per player

The $3 PDGA fee is already collected by TM, so the number you type into **Other fees** is
the donation **minus $3**. Worked examples:

| Gross entry | Donation | Other fees | Net entry left |
|---:|---:|---:|---:|
| $65 | $21 | **$18** | $44 |
| $30 | $12 | **$9** | $18 |
| $20 | $10 | **$7** | $10 |

Two obligations beyond the arithmetic: advertise the per-entry donation on the registration
page **before registration opens**, and send PDGA proof of donation (receipt or letter from
the charity) **within 30 days** of the event.

The 25% is *the* reduced payout. It is not a separate deduction, and it applies to pro
divisions exactly like am divisions. "Pro payouts are 25% less" is delivered through Other
fees, not through the Payouts tab.

⚠️ **There is no "75%" field anywhere in TM, and its absence is not a misconfiguration.** Once
Other fees is set, TM pays out **100% of the net entry purse** and the Payouts tab shows no
hold. A TD looking for the reduced payout will not find it and may conclude it was never
applied. Verified on a real CEP event: $65 entry, $18 Other fees, MP40 net purse $132,
projected payout $132.

📐 **The reduction is deeper than 25% of gross.** The $3 PDGA fee and the $3 match come off
*before* the 25% is taken on the remainder, so on a $65 entry the player keeps $44 — a **32.3%**
reduction, not 25%. Planning with "75% of gross" ($48.75) overstates the payout by $4.75 per
player. Use the net fee TM computes, never a percentage of gross.

🚫 **Never add a hold on the Payouts tab to "apply the 25%."** That double-counts the CEP
donation, and TM caps a deduction at 15% of net anyway (below), so a 25% hold is not enterable.

### Player packs and the am purse

On `/payouts_values`, an am division has five fields; a pro division has four (no pack
deduction). Set **player pack retail value** to what the pack is worth at retail. If you
leave **player pack deduction** blank, TM defaults the deduction to the retail value, which
drives the prize purse to $0 — that is the normal am model for a merch-pack event, and TM's
checklist stays green because value % is well over 100%.

Amateurs must receive at least 100% of net entry in value. An $80 retail pack against $44 of
net entry is 182%, so a generous pack leaves plenty of room for the CEP donation.

💰 **Every "value" field on this page is declared RETAIL, never cost — do not read any of them
into a budget as cash.** `PlayerPackValue` of $80 sits against a $26.31 cost basis, and
`TrophyValue` is what the trophy is worth, not what it was bought for. Declared trophy value
can easily run several times the actual trophy spend, a large overstatement if booked as an
expense. The only genuine cash number on any finance page is the
pro **Projected payout** on the Summary tab. These fields exist to drive the Value % compliance
calculation; they are not a cost ledger.

### Holds on a division's payout

Per-division on `/payouts_adjustments`, the field is "Add/deduct cash" for pros and
"Add/deduct prize value" for ams. **TM caps a deduction at 15% of that division's net entry
purse**, because Tour Standards require at least 85% of net entry to be paid out. The page
prints the ceiling as "Max deduction". Verified: $124 purse → max $18; $248 purse → max $37.

A hold stacks on top of the CEP donation, it does not replace it.

### Removing players in bulk

`/players_view` groups players by division with a REMOVE link per row. The link is
client-side only: it flips a hidden `remove_player[N]` field to 1 and swaps the link to
UNDO. Nothing is deleted until you submit, and **any one of the per-division Save buttons
submits the whole form**, so mark every row first and save once.

Two automation traps. Element refs captured before a page reload silently do nothing when
clicked, so re-locate after every save. And always confirm a mark landed by reading
`remove_player[N]`, because a failed click looks identical to a successful one.

## PDGA Tournament Manager — Layouts (verified contract, 2026-09-17)

There is **no layout write API** (v3 exposes only `layouts_read`), so layouts are managed through
TM's HTML forms as the TD. Captured from live TM pages and rehearsed end-to-end on
`stage.pdga.com` (a nightly backup of production — same event ids, same event password) — rehearse
there before writing to production.

| Step | Request | Fields | Notes |
|---|---|---|---|
| Login | `POST manager/{T}` | `txtPassword`, `cmdLogonSubmit=Login` | cookie session; failure re-renders "Please enter the event password" with HTTP 200 |
| Add layout | `GET manager/{T}/layout_add` → form posts to `manager/{T}/layout_edit` | `CourseID` (select), `Name`, `Holes`, `Length`, `Units` (`Feet`/`Meters`), `Accuracy` (`M`/`E`), `AddLayout=Add Layout` | **no per-hole fields here**; the response redirects to `layout_edit?LayoutID=<new>` — read the id from the URL |
| Hole detail | `GET/POST manager/{T}/layout_edit?LayoutID=<id>` | `Label{n}`, `Par{n}`, `Length{n}`, `Tee{n}`, `Target{n}`, `Notes{n}` (+ header fields), `EditLayout=Update` | verify with `layouts_read` → `layouts[id].Detail.H{n}` |
| Assign | `GET/POST manager/{T}/layouts` | `assignments[<DIV>][_][Rd<n>]=<layoutId>` (pool name replaces `_` when pools exist); submit button is unnamed | only layouts already added to the event are offered; verify with `layouts_read` → `layout_assignments[DIV].Rd<n>` |
| Clone template | `GET manager/{T}/layouts_select?no_chrome=1&course_id=<pdgaCourseId>` | `LayoutID_template` select lists every layout ever made for the course (other TDs' too) | useful to see what other events on the course have played |

Rules that bite:

- **Assignments need at least one registrant in the event.** With none, `/layouts` says "You must first add or upload player data" and renders no form; posted cells are silently dropped.
- **TM renders cells only for divisions with a registrant, but stores cells for any division you post** (`layouts_read` shows them). Post the event's full division list so late-registering divisions land on the right layout. A cell set for an unrendered division could not be cleared afterwards (`''` ignored, `0` → HTTP 500).
- **Played rounds are immutable in practice**: never repost a cell for a round with scores. PDGA Live `HighestCompletedRound` is the scored-round signal; `LatestRound` is merely the open round.
- **Look like a browser.** Full Chrome UA + Accept/Accept-Language/Sec-Fetch headers, `Origin`+`Referer` on POSTs, ~1-2 s human pacing. Non-browser clients get 429'd (server-hosted automation has failed to complete writes) and v3 `password_check` bursts get 403'd — one token per run.
- Round columns run `Rd1..RdN` plus `Rd10`, `Semis`, `Finals`, `Playoff` in `layouts_read`; the page shows only the event's configured rounds.

## Tournament Payouts

Compute a PDGA event's pro (and optional am cash/credit) payouts from the PDGA payout table,
assign them to final standings, and cross-check against what Tournament Manager publishes.
`payouts.py` only **computes and reports** — it never moves money. How winners actually get
paid (cash, PayPal, store credit, ...) is up to the TD; use the plan as the checked list.

### The pipeline

```
<event-dir>/payouts.yaml ─► payouts.py plan ─► (TM publish) ─► payouts.py plan (source: tm) ─► pay out
```

1. **Config** `<event-dir>/payouts.yaml`:
   ```yaml
   pdga_tournament_id: 12345
   event_name: My Tournament 2026   # optional; defaults to the PDGA Live name
   holes: 18                        # optional; warns on players with incomplete rounds
   divisions:
     MPO:  {mode: cash,   net_entry: 44, added_cash: 0}
     MP40: {mode: cash,   net_entry: 44}
     MA1:  {mode: credit, net_entry: 30}   # am prize value on the same curve
     MJ18: {mode: trophy}                  # no payout computed
   ```
   `mode` is `cash`, `credit` (non-cash am prize value) or `trophy`. Reading the YAML needs PyYAML
   (`pip install pyyaml`). Copy `net_entry` and
   `added_cash` from TM `/payouts_fees` and `/payouts_added_cash`.
2. **Plan:** `python3 scripts/payouts.py plan --event-dir <event-dir>` pulls final standings
   from PDGA Live, computes each paying division, compares to TM's published payouts, prints a
   summary and writes `payouts-plan.json`. Exit 1 = blockers.
3. **TM payouts** (see below) should be published so PDGA's record matches what is paid.
   Re-run the plan: each division should then show `source tm` or `source tm (event page)`.
4. **Pay out** from the plan's `prizes` list (name, PDGA#, place, amount, kind) by whatever
   method the event uses. Keep the plan JSON as the audit trail.

Other subcommands:

```bash
python3 scripts/payouts.py division --players 12 --fees 528 [--added 0]   # one division, per place
python3 scripts/payouts.py test                                           # regression vs sampled TM payouts
```

### How payouts are computed

- **Table:** PDGA's 2019 payout table, which TM uses ("The payout curves that are programmed
  into Tournament Manager are the same as in the 2019 spreadsheet", pdga.com/payout-calculator).
  Extracted verbatim to `data/pdga_payout_table_2019.json` (`Paypro`, 1-33 places paid;
  `PaypctP`, places paid by field size). Fields paying more than 33 places are not encoded; the
  script refuses them.
- **Cash line:** 40% of the field, rounded up (`PaypctP` 40% column equals `ceil(0.4n)` for
  n = 1-400).
- **Purse:** players × net entry + added cash. **Every registered pro counts, comps included.**
- **Rounding:** each place = round(entry-fee part) + round(added-cash part), half up; any
  remainder goes onto 1st (or comes off the last paid place). Against 113 sampled USD TM
  divisions (`tests/fixtures/tm_payouts_sample.json`, event IDs anonymised) this matches TM
  exactly on 56, including every division of the anchor event. Misses are TD edits, 45%/50%
  cash lines, or inputs the public API hides. Run `python3 scripts/payouts.py test`.
- **Ties for first: blocker.** PDGA CM 1.09.B requires a playoff (sudden-death or aggregate)
  for any tie for first, and 1.09.C forbids splitting first-place money evenly (exceptions only
  for flex-start departures or a weather-called final day). The plan blocks until the TD marks
  the playoff result in TM (Results page) and republishes payouts. Paying a tie for first as an
  even split is an easy mistake that then needs a correction.
- **Other ties:** tied players split the money of the places they occupy **evenly, to the cent**;
  a leftover cent goes to the first listed.
- **Versus TM:** hard stop if the division total, cash line or finishing order differ, or any
  place differs by more than **$5**. Inside that, **TM's numbers are used** (PDGA's record)
  and the differences show in the plan.

### Setting TM payouts when TM has none

`live_results_fetch_payouts?TournID=` answers **HTTP 404 with body `{"data":[]}`** when no
payouts are published (a real event with payouts answers 200). The script treats 404 as empty.

TM payouts are web-only (see "PDGA Tournament Manager Finance"). Two routes:
1. **TM's own payouts page** (`/payouts_adjustments?division=<DIV>`, then `/payouts_publish`):
   TM calculates each place from the same curve. **Verified in practice:** TM's "Suggested"
   column matched `payouts.py` to the dollar (field % 40, "Round to 5" is a separate column,
   leave it unused). Each row has a "Final payout" input per player (blank until set) and a
   "Declined" box. The Payouts page lists tied players at their separate place amounts
   (e.g. $190 / $129), but **the Publish page (`/payouts_publish`) splits ties itself in whole
   dollars** (e.g. $160 / $160, with a lower place dropping $1). That is within the $5
   tolerance, so after publish the plan uses TM's numbers. Only override "Final payout" if you
   want cents.
   Then click **Publish Payouts** (not "Publish Projected Payouts"); TM shows the green
   "Payouts have been published." banner (a ref-based click once failed silently: click the
   button by coordinate and look for the banner). The Prize column appears on the public
   event page `pdga.com/tour/event/<id>` immediately, but `live_results_fetch_payouts` can stay
   404/empty for 5+ minutes, so `payouts.py` falls back to the event page, comparing per
   player by PDGA#. Re-run `payouts.py plan` and confirm `source tm (event page)` or `tm`.
2. **Upload Player Data `Prize` column:** **not verified.** Test on a throwaway field before
   relying on it.

## Limitations

**PDGA API:**
- Rate limit: 300ms between requests
- Max 200 results per page (pagination automatic)
- `state_prov` filter on player search is unreliable — may return global results
- No historical membership snapshots — can only count current registrations
- Event search returns sanctioned events only by default
- Session tokens expire after ~24 hours

**DiscGolfScene:**
- Requires admin access to the tournament on DGS
- Session cookies expire periodically — re-run `dgs-auth.py` to refresh
- Registration export is a POST to the admin panel, not a public API
- Add-on columns vary by event — the parser auto-detects any column ending in ` $`
- Waitlist column uses `'1'` not `'YES'` — the parser handles both conventions
- All DGS management commands POST to known form endpoints — if DGS changes their form structure, run `discover` first to verify field names
- `create-discount-code` and `set-pools` use the AJAX fragment pattern (GET a template, parse the ID, then POST). If DGS changes the fragment format, these may break — re-run `discover` on the relevant page
- `clone-from` scrapes HTML to extract current values — best-effort regex parsing. Complex fields (AJAX-loaded items, JS-managed state) may not clone perfectly
- `set-staff` replaces all staff entries — it does not merge with existing staff. Include all staff members in every call
- The auth cookie names (`auth`, `c_r`, `c_m`) were discovered empirically — DGS may change them. `dgs-auth.py` captures all cookies regardless of name
- `dgs-auth.py` requires `DGS_EMAIL` and `DGS_PASSWORD` env vars (or `--email`/`--password` flags)

**Layouts & Scorecards:**
- PDGA Live layout data only exists for events that used PDGA live scoring, and only carries hole label/par/distance — no per-hole tee-sign notes
- Parkdly hole notes come from the primary tee sign's `noteText`; courses not built in Parkdly have no data
- The PDGA Live full-event pull makes one request per division × round (rate-limited 350ms) — a 15-division 2-round event takes ~10s
- `--pdf` needs Chrome/Chromium (auto-detected on macOS, or set `CHROME_PATH`)

**Tee Times & Sheets:**
- No generator script is bundled; pool assignments and division ordering are event-specific — defined in each event's own `tee-times.py`
- Card requests must be aggregated manually from several sources (DGS notes, email, DGS comments, TD sheet)
- Cross-pool card requests cannot be honored — note them as DENIED
- Google Sheets MCP cannot create tabs — use `gcloud auth print-access-token` + Sheets API `batchUpdate` for tab creation, renaming, colors, and formatting
- Pool colors must match the event's own `POOL_COLORS` — don't guess colors

## Output Format

All output is JSON to stdout. Errors are JSON to stderr with a non-zero exit code.
